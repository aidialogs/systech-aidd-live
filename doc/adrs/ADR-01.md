# ADR-01: Использование OpenAI Compatible API для интеграции с языковыми моделями

**Статус:** Принято  
**Дата:** 2025-10-10  
**Авторы:** Команда разработки

## Контекст

Для реализации Telegram-бота на базе LLM необходимо выбрать подход к интеграции с языковыми моделями. Требования:

- Возможность легко переключаться между различными провайдерами LLM
- Поддержка как облачных, так и локальных моделей
- Минимальная сложность реализации и поддержки
- Гибкость для будущего масштабирования

## Решение

Выбран подход **OpenAI Compatible API** в качестве единого интерфейса для работы с различными провайдерами языковых моделей.

### Ключевые принципы:

1. **Единый клиент** - используется библиотека `openai` для всех провайдеров
2. **Конфигурационное переключение** - смена провайдера через изменение `base_url` и `api_key`
3. **Абстракция через конфиг** - настройки провайдеров хранятся в конфигурационных файлах

### Поддерживаемые провайдеры:

**Облачные:**
- OpenAI (нативная поддержка)
- Azure OpenAI
- Groq
- Together.ai
- OpenRouter

**Локальные:**
- Ollama
- LM Studio
- vLLM
- Text Generation WebUI

## Последствия

### Положительные:

- ✅ **Простота реализации** - не требуется написание адаптеров для каждого провайдера
- ✅ **Быстрый старт** - минимальное время на первоначальную разработку
- ✅ **Легкое переключение** - смена провайдера через переменные окружения или конфиг
- ✅ **Тестирование** - возможность быстро тестировать разные модели
- ✅ **Локальная разработка** - простой переход на локальные модели (Ollama)
- ✅ **Cost optimization** - гибкость в выборе между дорогими и дешевыми провайдерами

### Отрицательные:

- ⚠️ **Ограниченная поддержка** - не все провайдеры совместимы (например, нативный Anthropic API)
- ⚠️ **Потеря специфичных фич** - некоторые уникальные возможности провайдеров могут быть недоступны
- ⚠️ **Зависимость от стандарта** - привязка к формату OpenAI API

### Риски и митигация:

- **Риск:** Провайдер не полностью совместим с OpenAI API
  - *Митигация:* Выбор провайдеров с полной поддержкой стандарта
  
- **Риск:** Необходимость использования специфичных фич провайдера
  - *Митигация:* Возможность расширения через адаптеры при необходимости

## Альтернативы

### 1. LiteLLM
**Описание:** Готовая библиотека для унификации доступа к 100+ провайдерам

- ✅ Поддержка большего числа провайдеров (включая Anthropic)
- ✅ Автоматическая конвертация форматов
- ❌ Дополнительная зависимость
- ❌ Меньший контроль над логикой

### 2. LangChain
**Описание:** Фреймворк для разработки LLM-приложений

- ✅ Богатая экосистема (chains, agents, RAG)
- ✅ Множество интеграций
- ❌ Большая и тяжелая зависимость
- ❌ Steep learning curve
- ❌ Избыточность для простого бота

### 3. Собственная реализация Strategy Pattern
**Описание:** Ручная реализация адаптеров для каждого провайдера

- ✅ Полный контроль над логикой
- ✅ Поддержка специфичных фич
- ❌ Высокая сложность разработки
- ❌ Необходимость поддерживать код для каждого провайдера
- ❌ Длительное время реализации

### 4. Микросервисная архитектура с Gateway
**Описание:** Отдельный сервис-шлюз для работы с LLM

- ✅ Независимое масштабирование
- ✅ Централизованное управление
- ❌ Избыточная сложность для MVP
- ❌ Требует инфраструктуры
- ❌ Overhead на поддержку

## Обоснование выбора

OpenAI Compatible API выбран как оптимальное решение по соотношению **простота / гибкость / время реализации**:

1. Позволяет быстро создать MVP
2. Покрывает 80% use cases проекта
3. Оставляет возможность для будущей миграции на более сложные решения
4. Минимизирует технический долг на начальном этапе
